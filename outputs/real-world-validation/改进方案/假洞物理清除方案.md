# 假洞物理清除方案（草案 v1）

> 状态：施工蓝图，未实施。基线 commit `b71cf52`。
> 关联差距：露露姨 door_details 总数仍 26（语义已收敛为 3 door + 16 opening + 7 unverified，假洞未物理清除），下游各自过滤存在口径不一致风险。

## 1. 问题

`build_door_details`（`core/pdf_plan_reader.py` L1692）输出扁平列表：每个洞口一条记录，含 `door_type`（door / opening / unverified）、`confidence`、`evidence`（含 `wide_arc_downgrade` 留痕）。语义收敛后，26 条记录中大量是"已判定为假门/超宽洞口"的数据，但它们在数据结构上与前 5 条真洞平起平坐。

下游目前各自为政地过滤：

- 预算：`_counts_as_interior_door`（`core/budget_estimate.py` L348）——door→计；opening ≤1200mm→计；超宽/unverified→不计；
- 布局：`layout_draft` 按 `op["kind"]=="door"` 取门位（多处：L67/L354/L447/L606/L624），对 unverified 与超宽 opening 的处理与预算口径**不一致**；
- 融合/闸门另有各自读法。

口径不一致已经在事实上发生过（预算门分项改前 23 樘 vs 布局摘要门 21 个 vs door_details 26 条——三个数字三个口径）。随着消费方增多，每加一个下游就要重新发明一次过滤，错误只是时间问题。

## 2. 根因诊断：为什么保留假洞当时是对的，现在为什么要分层

**当时对**：语义收敛（门宽物理先验降级）是启发式判定，存在误判可能。扁平保留 + evidence 留痕保证了可回溯——任何"被降级的门"都能查出原判定依据，这是项目诚实化机制的一部分，也是罗菁回归零漂移的安全网。

**现在要分层**：问题不在"保留"，而在"无结构的保留"——所有记录同一层级，可信的与可疑的混放，默认读取 = 全读。分层的目标不是删除假洞，而是：

1. **默认安全**：下游不做任何过滤时拿到的就是可信集；
2. **口径唯一**：全项目只有一处定义"什么算室内门"；
3. **留痕不丢**：rejected 区完整保留 evidence，可回溯性与现状等价。

## 3. 候选方案对比

| 方案 | 原理 | 优点 | 缺点 | 误伤风险 |
|---|---|---|---|---|
| a. 数据三分区 | `door_details` 改为 `{"confirmed": [...], "openings": [...], "rejected": [...]}`，写入侧一次性分拣 | 默认安全最彻底；结构自解释 | 改数据结构，所有现存读取点（含 12 个验收脚本的断言、融合脚本）都要适配；向后兼容成本高 | 低（分拣规则=现行语义规则平移） |
| b. 统一访问层 | 数据不动，新增 `get_doors(details, level="usable")` 访问函数，全项目消费方收口到一处 | 数据结构零改动，留痕天然保留；过滤逻辑单点定义；可分级（usable / countable / all） | 靠纪律保证"大家都走访问层"，遗漏一个消费点就打回现状 | 低 |
| c. 保守派 | 数据不动，只把 `_counts_as_interior_door` 逻辑复制推广到布局模块 | 改动最小 | 过滤逻辑变成两处副本，已是不一致的病根；不治本 | 低 |

## 4. 推荐方案：b（统一访问层）为骨干，吸收 a 的分级语义

选 b 的理由：项目处于"双图样本、规则快速演进"阶段，数据结构的稳定性比形式 purity 重要——12 个验收脚本与融合管线都建立在现有扁平结构上，方案 a 的结构变更会触发大面积断言适配，且每次语义规则演进都要重新考虑分区归属。访问层用函数封装分级语义，规则演进只改一处。

分级定义（吸收方案 a 的语义，但不改存储）：

| level | 含义 | 包含 |
|---|---|---|
| `usable` | 布局/概念可用的真门位 | door_type==door 且 confidence ≥0.6 |
| `countable` | 预算工程量计数口径 | usable + opening ≤1200mm（即 `_counts_as_interior_door` 现逻辑） |
| `openings` | 全部已采信通行洞口（含降级） | door + opening（不含 unverified） |
| `all` | 全量含留痕 | 26 条原样 |

## 5. 验收标准

1. 新增 `validate_door_access.py`：四个 level 在露露姨数据上分别返回预期集合（usable=3 / countable=5 / openings=19 / all=26）；罗菁数据 usable=6 / countable=8；
2. 口径归一：同一图纸下，预算门分项樘数 = 布局摘要门数（露露姨均为 5，罗菁均为 8）——断言写在泛化脚本里；
3. 双图基线零漂移：露露姨预算总价 5.81–9.54 万、罗菁门分项 1.12–1.76 万不变；
4. **13 个验收脚本全绿**（12 既有 + 新访问层脚本）；
5. rejected/unverified 记录的 evidence 在 `all` level 下逐条完整（留痕不丢回归断言）。

## 6. 风险与不做清单

**风险**：
- 访问层推广依赖"消费方全部改道"，漏一处即口径分裂复发 → 缓解：实施第 4 步用全局 grep（`op["kind"]`、`door_type`、`door_details[`）列出全部读取点并逐一核对，清单入 commit message；
- level 语义是新的项目术语，未来贡献者可能绕过 → 缓解：`build_door_details` docstring 顶部注明"消费方必须经 get_doors 读取"；
- 布局事实构建改道后，门位选择可能微妙变化（usable 门槛 confidence ≥0.6）→ 用罗菁布局产物 diff 锁定，差异超一个门位即回查。

**不做清单**（防止范围蔓延）：
- 不改 `door_details` 扁平存储结构、不改 `build_door_details` 输出字段（方案 a 整体排除）；
- 不做假洞的物理删除（rejected 永留痕）；
- 不新增门语义判定规则（usable/countable 判定只能平移现行规则，不得借机"顺手改进"）；
- 不动窗的检测与数据结构；
- 不动闸门分级（`layout_degraded` 机制）；
- 不引入新 Python 依赖；
- 不重构 `_normalize_facts` 中与门无关的部分。
